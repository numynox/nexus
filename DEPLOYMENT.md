# Deployment

How Nexus is hosted, released and recovered. `README.md` covers local
development; the reasoning behind these choices is in `.agents/brain/decisions/`.

CI publishes the frontends and applies migrations; Edge Functions and secrets
are still pushed by hand:

| What | How | Automated? |
| :--- | :--- | :--- |
| Database migrations | GitHub Actions, on push to `main`, before the websites | yes |
| The websites | GitHub Actions → GitHub Pages | yes |
| The Android apps | GitHub Actions → GitHub Releases, sideloaded | yes |
| Edge Functions | `npm run db:functions:deploy` from a laptop | no |
| Vault / function secrets | Supabase dashboard or CLI | no |

A merge to `main` applies its migrations and only then publishes the websites,
so a schema change and the frontend that needs it can merge together. A change
that touches an **Edge Function** still needs the function deployed by hand
**first**, or the newly published site calls a function that does not have it
yet. Pull requests never touch the live database: they run the database tests
against a local stack (`database-tests.yml`).

---

## Hosting

- **Frontend:** GitHub Pages, from the `numynox/nexus` repository.
- **Backend:** one Supabase project (`nexus`) — Postgres, auth, Edge Functions,
  `pg_cron`, Vault.
- **External API:** [Tankerkoenig](https://creativecommons.tankerkoenig.de/) for
  fuel prices.

All the apps are published into one Pages site as siblings:

| Page | URL |
| :--- | :--- |
| Landing | `https://numynox.github.io/nexus/` |
| Noctua | `https://numynox.github.io/nexus/noctua` |
| Vibilia | `https://numynox.github.io/nexus/vibilia` |
| Annona | `https://numynox.github.io/nexus/annona` |
| Abeona | `https://numynox.github.io/nexus/abeona` |

The landing page is generated by `npm run build:landing` from `config.yaml`, so
its names, descriptions and links cannot drift from the apps. The
`/nexus/<app>` prefixes are compiled into every internal link at build time, so
the apps only work under those paths.

## Website deploy (automated)

`.github/workflows/deploy-pages.yml`:

1. Triggers on **push to `main`**, or manually via `workflow_dispatch`.
2. Job `migrate` (main only) applies the migrations the live database lacks
   (see "Database deploy" below). The website jobs wait for it; if it fails,
   nothing is published.
3. Node 22, `npm ci` at the repository root (one workspace install for every
   app). Astro 7 requires Node ≥ 22.12.
4. `npm run build:websites` — builds Noctua, Vibilia, Annona and Abeona in sequence into
   `output/pages/<app>`, then writes the landing page at `output/pages/index.html`.
5. Uploads `output/pages` as the Pages artifact and deploys it.

Runs are never cancelled midway (one may be applying a migration); a newer
push waits for the running one.

> **A merge to `main` is a release.** There are no release tags; `main` is
> always what is live. Merge only work that is ready to be published — see
> `.agents/brain/decisions/2026-09-04-main-is-the-release-branch.md`.

### Required GitHub repository variables

Set as **variables** (not secrets) — they are baked into the published bundle,
which is expected: the anon key is a public key and all authorization is
enforced by RLS.

- `PUBLIC_SUPABASE_URL`
- `PUBLIC_SUPABASE_ANON_KEY`
- `PUBLIC_CARTO_API_KEY` — basemap tiles for Vibilia's nearby map. Optional: if
  it is unset the map falls back to OpenStreetMap tiles instead of CARTO's
  watermarked ones. Request one at
  [carto.com/basemaps/apikey](https://carto.com/basemaps/apikey/) — free within
  5 million tile requests a month, no CARTO account needed.

Changing any of them requires a rebuild; there is no runtime configuration.

### Failure modes

- Missing variables do not fail the build. The apps compile, then every request
  from the browser fails with "Missing PUBLIC_SUPABASE_URL…".
- All the builds run `astro check` and `svelte-check` first, so a type error in
  an `.astro`, `.ts` or `.svelte` file fails the deploy rather than shipping.

## Android app release (automated)

Each native app (`android/`, see
`.agents/brain/decisions/2026-10-19-native-android-apps.md`) has its own
workflow — `android-noctua.yml`, `android-vibilia.yml`, `android-annona.yml`,
`android-abeona.yml` — and all of them call the same build, `android-app.yml`
(`.agents/brain/decisions/2026-10-19-shared-android-build-and-per-app-ci.md`):

1. Triggers on pull requests and pushes to `main` that touch **that app's
   module or the shared Android code** (`android/core`, `android/build-logic`,
   the Gradle files) or `config.yaml`, and on `workflow_dispatch`. A change to
   Noctua alone builds Noctua alone.
2. One Gradle run, Java 21: the unit tests and the screenshot walk
   (`:<app>:recordRoborazziDebug`), the shared modules' tests
   (`:core:data` and `:core:update`), then `:<app>:assembleRelease`. The Gradle
   cache is written from `main` only and read by pull requests.
3. On a push to `main` with the signing key configured, publishes a GitHub
   release tagged `<app>-android-v<version>` with the APK attached. The
   version is `0.0.<run number>`; its prefix is set in one place,
   `android/build-logic/src/main/kotlin/NexusApplicationPlugin.kt`.
   Pull requests only keep the APK as a 14-day build artifact.

The version code is the app's workflow run number, so every release is newer
than the last — **do not rename an `android-<app>.yml`**: a new file name
starts counting at one, and Android refuses to install a lower version code
over a higher one. Releases are created with `--latest=false`, so no app's
release becomes the repository's "latest" over another's; each app's update
check looks only at tags with its own prefix.

### Installing and updating on a phone

**The first install** is by hand: open the release page on the phone,
download the APK and install it (Android asks once to allow installs from the
browser).

**Every later update happens inside the app**
(`.agents/brain/decisions/2026-11-09-in-app-self-update.md`). The app checks
GitHub's releases on start and once a day, notifies a newer release once, and
offers it in a banner and at the foot of Settings. "Install" downloads the APK,
checks it is the same app, newer and signed with the same key, and hands it to
Android's package installer; the app restarts as the new version, keeping its
sign-in and settings. The first time, Android asks to allow "Install unknown
apps" for the app itself and to confirm the update. Later updates may install
without the prompt — not yet seen on a device, so check it on the next two
releases. There is no Play Store listing.

Debug builds (`.debug`) are another package and debug-signed: their banner
opens the release page instead.

### Required configuration

The same repository **variables** as the websites — `PUBLIC_SUPABASE_URL`,
`PUBLIC_SUPABASE_ANON_KEY`, `PUBLIC_CARTO_API_KEY` — are baked into the APK.
Changing them means a new release *and* every phone updating.

Repository **secrets** for signing:

| Secret | What |
| :--- | :--- |
| `ANDROID_KEYSTORE_BASE64` | the release keystore, `base64 -w0 release.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | the keystore's password |
| `ANDROID_KEY_ALIAS` | the key's alias inside it |
| `ANDROID_KEY_PASSWORD` | the key's password |

Create the keystore once:

```bash
keytool -genkeypair -v -keystore release.jks -alias nexus \
  -keyalg RSA -keysize 4096 -validity 10000
```

To sign a release build on your own machine with the same key, set the four
variables above (`ANDROID_KEYSTORE_PATH` in place of the base64 one), or put
them in the gitignored `android/keystore.properties`; a variable wins over the
file:

```properties
storeFile=/path/to/release.jks
storePassword=…
keyAlias=nexus
keyPassword=…
```

A relative `storeFile` is resolved against `android/`. To install a local
release build over a released app, pass the installed version's
`NEXUS_VERSION_CODE` (an equal code installs) — never a lower one, which
Android refuses without an uninstall (and its loss of the app's data), and
never a high one like 9999, which would make every later release a downgrade
the app ignores.

**Back the keystore up outside GitHub.** Android installs an update only if it
is signed with the same key as the installed app; without the key, every phone
has to uninstall (losing local settings) and install afresh. One key signs all
Nexus apps.

### Failure modes

- Without `ANDROID_KEYSTORE_BASE64` the build still runs, debug-signed, warns,
  and publishes nothing. A debug-signed APK cannot update an installed app:
  each runner makes its own debug key. So pull requests from this repository
  are release-signed as well, and their `<app>-apk` artifact installs over the
  released app; a fork's pull request gets no secrets and stays debug-signed.
- Without the Supabase variables the APK builds and its sign-in screen says the
  build has no Supabase connection configured.
- An installed APK outlives a schema change far longer than a website does: a
  migration must not drop or rename anything an older app still reads.

## Database deploy (automated)

The `migrate` job in `deploy-pages.yml` runs `supabase db push --db-url
"$SUPABASE_DB_URL" --yes` on every push to `main`: it applies the files in
`supabase/migrations/` that are missing from the live history
(`supabase_migrations.schema_migrations`) and changes nothing when none are.
It uses the same history as the manual methods below, so they can be mixed.
Reasoning: `.agents/brain/decisions/2026-11-11-migrations-deployed-by-ci.md`.

### Required GitHub environment secret

- `SUPABASE_DB_URL`, on the GitHub **environment `main`** — the **session pooler** connection string, from the
  Supabase dashboard → **Connect** → *Session pooler*:
  `postgresql://postgres.<project-ref>:<password>@aws-<n>-<region>.pooler.supabase.com:5432/postgres`.
  Not the direct connection: on the free plan it is IPv6-only, and GitHub's
  runners have no IPv6. Percent-encode special characters in the password.
  Set it under Settings → Environments → `main` → **Environment secrets** (not
  a repository secret, not a variable: it is the database password). Only the
  `migrate` job names that environment, so no other workflow — a pull
  request's included — can read it. The environment has no required
  reviewers: merging is the approval.

### Pull requests

`.github/workflows/database-tests.yml` starts a local Supabase stack in the
runner, applies every migration to it and runs `supabase/tests/` — on every
pull request that touches migrations, tests, the seed or `config.toml`. It has
no secret and never connects to the live project.

### Failure modes

- Without `SUPABASE_DB_URL` the `migrate` job fails with an error naming the
  secret, and the websites are not published. Nothing is half-done.
- A migration that fails rolls back on its own; the job fails and the websites
  are not published. Migrations before it in the same push stay applied.
- The rule from the Android section still holds: a migration must not drop or
  rename anything an older app still reads. CI applies it the moment it
  merges.

## Database deploy (manual)

Still useful to apply a migration before its merge, or without GitHub.
Requires the Supabase CLI logged in and the project linked:

```bash
npm run db:login
npm run db:link -- --project-ref <your-project-ref>
```

Then, from the repository root:

```bash
npm run db:migrations:list   # what the remote has
npm run db:push:dry-run      # what would be applied
npm run db:push              # apply
```

Migrations in `supabase/migrations/` are shared by every app — there is no
per-app database release. Take a backup before pushing anything destructive.

### Without the CLI: one paste into the SQL editor, even on a phone

When the CLI is not at hand (a phone, a cloud session), let the database fetch
the migration from GitHub and run it, **in one statement, whatever the
migration's size**. The repository is public, and the `http` extension
(`20261102160000_http_extension.sql`) downloads synchronously.

Fill in the three placeholders and paste this into **SQL Editor → New query**:

```sql
do $$declare r extensions.http_response:=extensions.http_get('https://raw.githubusercontent.com/numynox/nexus/<commit>/supabase/migrations/<version>_<name>.sql');begin if r.status<>200 then raise exception 'Download failed: HTTP %',r.status;end if;execute r.content;insert into supabase_migrations.schema_migrations(version,name)values('<version>','<name>');end$$;
```

- `<commit>`: a commit that contains the file, short hashes work. Pin a
  **commit**, never a branch, so the file cannot change between review and run.
- `<version>_<name>`: the file name, e.g. `20261102140000_abeona_function_grants`.
- It runs the whole file and adds the row to the CLI's migration history, so
  `npm run db:migrations:list` and a later `npm run db:push` see it as applied.
- One `do` block is one transaction: if the download or any statement fails,
  nothing is applied, not even the history row.

Check it afterwards with `npm run db:migrations:list`, or in the editor:
`select version, name from supabase_migrations.schema_migrations order by version desc limit 3;`

On a fresh project without `http`, run `create extension if not exists http
with schema extensions;` once first. `pg_net` would also work, but it answers
asynchronously, so it needs two pastes a few seconds apart. That was how
`20261102120000_abeona_foundation` went in, after the MCP tool's confirmation
prompt timed out.

## Edge Function deploy (manual)

```bash
npm run db:functions:deploy                      # all functions
npx supabase functions deploy fetch-rss          # one function
npm run db:functions:list                        # what is deployed
```

| Function | Invoked by | Authenticates with |
| :--- | :--- | :--- |
| `fetch-rss` | `pg_cron`, hourly | `FETCH_RSS_INVOKE_SECRET` as a bearer token |
| `refresh-fuel-prices` | `pg_cron`, every 10 minutes | `FUEL_PRICE_INVOKE_SECRET`, bearer or `x-invoke-secret` |
| `fetch-nearby-fuel-prices` | Vibilia's browser UI | the signed-in user's JWT |
| `lookup-food-product` | Annona's browser UI | the signed-in user's JWT |
| `abeona-transit` | both Abeona clients | the signed-in user's JWT |
| `abeona-refresh-trips` | `pg_cron`, every 10 minutes | `ABEONA_REFRESH_INVOKE_SECRET`, bearer or `x-invoke-secret` |
| `abeona-import` | both Abeona clients (Träwelling import) | the signed-in user's JWT |
| `abeona-public` | anyone holding an Abeona share link | nothing: the token in the link (`verify_jwt = false`) |

`supabase/config.toml` sets `verify_jwt = false` for the three scheduled functions
— they are guarded by the shared secret instead, and must never be deployed
without it configured. The ones called from a client verify JWTs. The one
exception is `abeona-public`, which is open on purpose: it answers only for a
share link's unguessable token, through `abeona_shared_trip()`, and only with
a trip's route and times (`.agents/brain/decisions/2026-11-04-abeona-share-links.md`).

`lookup-food-product` needs no secret at all: Open Food Facts is public and
identifies callers by User-Agent. Nor does `abeona-transit`: Transitous is
public, free for non-commercial use, and asks for attribution, which both
Abeona clients show in Settings.

### From a cloud session (Claude on the web or phone)

A cloud session has no Supabase login for the CLI, but the **Supabase
connector** (claude.ai → Settings → Connectors) deploys a function directly:
its `deploy_edge_function` tool uploads the files and makes the new version
live at once. That is the easiest way without a laptop. Ask for it in the
chat ("deploy abeona-transit"). It is a production change that takes effect
at once, so the deploy should be confirmed first.

To match what `npm run db:functions:deploy` produces, the deploy must:

1. **Lay files out as the CLI does:** names relative to `supabase/`, e.g.
   `functions/abeona-refresh-trips/index.ts`, with `entrypoint_path` set to
   that index file.
2. **Include every file the function imports, recursively, and nothing
   else.** Tests (`*.test.ts`) and `fixtures/` stay out. The Abeona functions
   import from `functions/abeona-transit/` (`contract.ts`, `transitous.ts`,
   `cache.ts`, `refresh.ts`, `polyline.ts`, …), so those files go with
   `abeona-import`, `abeona-public` and `abeona-refresh-trips` too; after a
   change to a shared file, deploy every function that imports it.
3. **Take `verify_jwt` from `supabase/config.toml`, never the tool's default
   (`true`).** `fetch-rss`, `refresh-fuel-prices`, `abeona-refresh-trips` and
   `abeona-public` need `false`: with `true` the scheduled jobs and share
   links stop working.
4. **Pass the import map** where `config.toml` names one (`fetch-rss` and
   `refresh-fuel-prices`: their `deno.json`, uploaded and given as
   `import_map_path`).
5. **Deploy from committed code.** Deploy what is on `main` (or about to merge),
   so the repository stays the authoritative copy (`supabase/README.md`).

Afterwards, `get_edge_function` shows the deployed version, its `verify_jwt`
and its files: compare them with the plan. It lists the files without the
leading `functions/` (`refresh-fuel-prices/index.ts`); that is expected. Then
watch the function's next calls (Logs → Edge Functions, or the connector's
log query): the version number is on each call.

Tested on 2026-11-12 with `refresh-fuel-prices` (version 6, unchanged code):
every cron call since answered 200. Functions that import from another
function's folder (the Abeona ones) have not been deployed this way yet. Secrets are separate: the
connector does not set them (dashboard → Edge Functions → Secrets, or
`supabase secrets set` from a laptop).

**Abeona's first release** needs its database half first: push
`20261102120000_abeona_foundation.sql` (it also creates the private
`abeona-tickets` Storage bucket and its policies), then deploy
`abeona-transit`, then merge the clients.

**Abeona's after-the-ride release** (#38 phase 5) goes in this order:

1. Push the migrations `20261103140000_abeona_final_actuals` up to
   `20261103180000_abeona_refresh_trips_schedule` (one paste each works too).
   The last one schedules `abeona-refresh-trips-every-15min`, which raises on
   every tick until steps 2 and 3 are done; that is harmless.
2. Set the function's secret and deploy it:
   `npx supabase secrets set ABEONA_REFRESH_INVOKE_SECRET=<secret>` and
   `npx supabase functions deploy abeona-refresh-trips`. Deploy
   `abeona-transit` again too: it now imports its refresh from `refresh.ts`,
   which the new function shares (`../abeona-transit/refresh.ts`).
3. Create the two Vault secrets `ABEONA_REFRESH_INVOKE_SECRET` (the same value)
   and `ABEONA_REFRESH_FUNCTION_URL` (below).
4. Merge the clients. An older APK keeps working: nothing it reads was
   renamed or dropped.

The job must run on the day: Transitous carries a day's realtime only until
shortly after, so a trip the job missed keeps its last live values.

**Abeona's history and polish release** (#38 phases 6–7) goes in this order:

1. Push the migrations `20261104090000_abeona_history` up to
   `20261104120000_abeona_orphaned_files`. Older APKs keep working: only
   columns, fields and tables were added, and `abeona_save_trip` and
   `abeona_statistics` kept their signatures.
2. Deploy the functions: `abeona-transit` (the response cache and the stops'
   country), `abeona-refresh-trips` (the cache, and it now removes up to 20
   orphaned ticket or card files a run), and the two new ones,
   `abeona-import` and `abeona-public`. `npm run db:functions:deploy` does all
   of them. No new secrets: the service role key is injected by the
   platform, and Träwelling tokens come from the user with each request.
3. Merge the clients. The web's status page (`/nexus/abeona/status?t=…`) is
   what status links point at, so it must be live before anyone shares one;
   the Android app builds the same URL (`AbeonaRepository.STATUS_PAGE`). A
   Pages URL other than `numynox.github.io/nexus` means changing that
   constant too.

**Abeona's per-traveller BahnCard discount** needs
`20261104130000_abeona_traveller_discounts` pushed before the clients merge:
they call `abeona_save_trip_travellers` and send `p_trip.travellers`. Older
APKs keep working; the migration only adds a column, a trigger and functions,
and redefines three functions with their signatures unchanged
(`.agents/brain/decisions/2026-11-04-abeona-discount-per-traveller.md`).

Supabase rewrites `text/html` from Edge Functions to `text/plain` on its own
domain, which is why the status page is a static page that fetches JSON from
`abeona-public` rather than HTML served by the function. The `.ics` file is
served by the function directly.

### Edge Function secrets

Dashboard → Project Settings → Edge Functions → Secrets, or:

```bash
npx supabase secrets set FETCH_RSS_INVOKE_SECRET=<secret> --project-ref <ref>
```

## Scheduling and Vault secrets

The cron jobs live in migrations, so `db:push` installs them. They call SQL
wrappers that read their secrets from **Supabase Vault** and POST to the Edge
Function through `pg_net`. The Vault entries are *not* in migrations and must be
created per environment:

| Vault secret | Example value |
| :--- | :--- |
| `FETCH_RSS_INVOKE_SECRET` | the same secret as the function's |
| `FETCH_RSS_FUNCTION_URL` | `https://<ref>.supabase.co/functions/v1/fetch-rss` |
| `FUEL_PRICE_INVOKE_SECRET` | the same secret as the function's |
| `REFRESH_FUEL_PRICES_FUNCTION_URL` | `https://<ref>.supabase.co/functions/v1/refresh-fuel-prices` |
| `ABEONA_REFRESH_INVOKE_SECRET` | the same secret as the function's |
| `ABEONA_REFRESH_FUNCTION_URL` | `https://<ref>.supabase.co/functions/v1/abeona-refresh-trips` |

Dashboard → Project Settings → Vault, or:

```sql
select vault.create_secret('<secret>', 'FETCH_RSS_INVOKE_SECRET');
select vault.create_secret('https://<ref>.supabase.co/functions/v1/fetch-rss', 'FETCH_RSS_FUNCTION_URL');
select vault.create_secret('<secret>', 'FUEL_PRICE_INVOKE_SECRET');
select vault.create_secret('https://<ref>.supabase.co/functions/v1/refresh-fuel-prices', 'REFRESH_FUEL_PRICES_FUNCTION_URL');
select vault.create_secret('<secret>', 'ABEONA_REFRESH_INVOKE_SECRET');
select vault.create_secret('https://<ref>.supabase.co/functions/v1/abeona-refresh-trips', 'ABEONA_REFRESH_FUNCTION_URL');
```

The Tankerkoenig key is deliberately **not** in Vault: only the Edge Functions
use it, and they read it from their own environment.

Rotating an invoke secret means changing it in **both** places — Vault and the
function's environment — or the job starts getting 401s.

### Current schedule

| Job | Cron | Calls |
| :--- | :--- | :--- |
| `fetch-rss-hourly` | `7 * * * *` | `public.invoke_fetch_rss()` |
| `refresh-fuel-prices-every-10min` | `7,17,27,37,47,57 * * * *` | `public.invoke_refresh_fuel_prices()` |
| `nexus-maintenance-daily` | `17 3 * * *` | `public.run_nexus_maintenance()` |
| `abeona-refresh-trips-every-10min` | `7,17,27,37,47,57 * * * *` | `public.invoke_abeona_refresh_trips()` |

All jobs run on the same minutes on purpose: every 2-minute window in which
anything writes costs a whole 16 MB WAL segment of Disk IO, so a new job goes
on these minutes, never beside them
(`.agents/brain/decisions/2026-11-05-scheduled-jobs-share-minutes.md`).

`nexus-maintenance-daily` never leaves the database — no Edge Function, no Vault
secret — so unlike the other two it reports its own outcome. It returns a JSON
summary of rows touched per step, which `cron.job_run_details` records:

```sql
select start_time, return_message
from cron.job_run_details
where jobid = (select jobid from cron.job where jobname = 'nexus-maintenance-daily')
order by start_time desc limit 7;
```

### Verifying and debugging a job

```sql
select jobid, jobname, schedule, active from cron.job;
select * from cron.job_run_details order by start_time desc limit 20;
```

`pg_net` calls are fire-and-forget: a cron run is recorded as successful even
when the Edge Function fails. To see what the function did, read its logs in the
dashboard. To invoke either function by hand, use the Bruno collection in
`.bruno/supabase/`.

`abeona-refresh-trips` answers with a JSON summary (`trips`, `finalized`,
`failed`, one result per trip), visible in the function's logs. Whether trips
were frozen shows in the data too:
`select count(*) from abeona_trips where finalized_at > now() - interval '1 day';`

Nothing alerts on failure. If prices or articles look stale, check
`cron.job_run_details` first, then the function logs.

## Backups and recovery

The free tier has no point-in-time recovery, so backups are manual scripts
(`.agents/brain/decisions/2026-04-17-manual-supabase-backups.md`). They run
against the **linked remote** project and write to `backups/supabase/<timestamp>/`
(git-ignored).

```bash
npm run db:backup                                          # public schema
SUPABASE_BACKUP_SCHEMAS=auth,storage,public npm run db:backup
```

Rehearse a restore locally before trusting it:

```bash
npm run db:restore:local -- backups/supabase/<timestamp>
```

The local restore rebuilds the schema from `supabase/migrations/` and then loads
only the backup's **data**, so a restored database is always at the current
schema version — old backups work without any per-migration fix-ups.

Restoring a backup taken before the fuel price rollup existed leaves
`fuel_prices_daily` empty. Nothing breaks — the weekly minima RPC falls back to
raw readings and the prune refuses to delete anything — but rebuild it with
`select public.rollup_fuel_prices_daily();` to get the aggregated history back.

Because the default backup covers `public` only, a local restore brings data but
not users; ids will not match. Repoint ownership with:

```sql
select public.reassign_profile_user(
  'old-profile-user-id'::uuid,
  'new-auth-user-id'::uuid,
  true   -- merge into an existing target profile and drop the source
);
```

It reassigns Noctua's `sections` and `article_reads` (deduplicating) and
Vibilia's `cars.owner_id`, `car_access`, `refuel_events` and `car_expenses`.

A remote restore is the mirror image: there the schema comes from the backup
snapshot, because the point is to put the database back exactly as it was. If
that snapshot predates the latest migrations, follow it with `npm run db:push`.
The script prints this reminder.

### Remote restore (destructive)

Drops and recreates `public` on the remote project. Take a fresh backup first,
and only do this deliberately:

```bash
SUPABASE_DB_URL='postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres' \
  npm run db:restore:remote -- backups/supabase/<timestamp> --confirm-remote-restore
```

## Reclaiming database space

Retention runs nightly (see the schedule above), but Postgres does not return
freed space to the operating system on its own: a `DELETE` only marks the rows
reusable. After the first maintenance run — or any other large cleanup — the
dashboard number moves only once the tables are rewritten.

Run it once by hand after deploying the retention migrations:

```sql
-- 1. Aggregate, then prune. Safe to repeat; reports what it touched.
select public.run_nexus_maintenance();

-- 2. Check the charts still look right in Vibilia before reclaiming.

-- 3. Rewrite the tables. Brief exclusive lock; seconds at this size.
vacuum full public.fuel_prices;
vacuum full public.articles;
reindex table public.fuel_prices;
reindex table public.articles;

-- 4. pg_net's log is a log: truncating returns the space immediately.
truncate net._http_response;
```

Measured against a restored production backup (2026-09-05): `fuel_prices` fell
from 71 MB to 7.9 MB, `articles` from 19 MB to 10 MB, and `fuel_prices_daily`
cost 560 kB. `VACUUM FULL` cannot run inside a transaction, so it can never be
part of a migration.

To see where the space actually is:

```sql
select relname, pg_size_pretty(pg_total_relation_size(c.oid)) as total
from pg_class c join pg_namespace n on n.oid = c.relnamespace
where c.relkind = 'r' and n.nspname in ('public', 'net', 'cron')
order by pg_total_relation_size(c.oid) desc limit 10;
```

## Backfilling Annona from Open Food Facts

Products added before the barcode lookup existed carry only what was typed by
hand. `scripts/backfill-openfoodfacts.mjs` fills the gaps — nutrition above
all, plus an image where there is none.

It runs on your machine and writes to whichever database the env file points
at, so the target is chosen by the npm script: `db:backfill:off` uses `.env`
(local), `db:backfill:off:prod` uses `.env.prod` and passes `--confirm-prod`,
which the script demands before writing anywhere that is not localhost.

Requires `20260905170000_annona_products_off_checked_at.sql` — push it first, or
the first update fails.

```bash
npm run db:push                                        # the off_checked_at column

npm run db:backfill:off -- --limit 10 --dry-run        # rehearse locally
npm run db:backfill:off:prod -- --limit 25 --interactive
```

Two things make it safe to run repeatedly:

- **What you typed wins.** `name`, `brand` and `quantity` are filled only when
  empty. A difference is reported, and with `--interactive` put to you per
  field — keep yours, take theirs, type a replacement, or answer once for every
  remaining conflict.
- **Every product is stamped**, found or not, so a second run skips it. Stop the
  run whenever you like; progress is saved per product. `--refresh` re-checks
  products stamped long ago, since Open Food Facts gains data over time.

Open Food Facts allows **15 product requests per minute per IP**, so the default
pace is one every five seconds — 126 products take about eleven minutes. Run it
from your own machine rather than an Edge Function: the limit is per IP, and
Supabase's is shared. On HTTP 429 the script waits once, then stops rather than
hammering. Above a few hundred products, Open Food Facts asks that you use their
CSV/JSONL exports instead of the API.

Set `OFF_CONTACT` to an email address to identify yourself the way their policy
asks; the repository URL stands in otherwise.

## Standing up a new environment

Order matters:

1. Create the Supabase project; note the ref, URL, anon key and service key.
2. `npm run db:login` and `npm run db:link -- --project-ref <ref>`.
3. `npm run db:push` — schema, RPCs, RLS and the cron jobs. Expect the jobs to
   raise on every tick until step 5.
4. Deploy the functions and set their secrets (above).
5. Create the Vault secrets (above).
6. Create user accounts in the dashboard. **The apps have no sign-up screen** —
   sign-in only, by design.
7. Set `PUBLIC_SUPABASE_URL` and `PUBLIC_SUPABASE_ANON_KEY` as GitHub repository
   variables, then run the Pages workflow. For the Android apps, also add the
   signing secrets (above) and run the Android workflows.
8. Optionally seed: `npm run db:seed:fuel-prices`, `npm run db:seed:products`,
   or `supabase/seed.sql` for feeds and stations.

Note that granting anyone an account gives them full read/write access to
Annona's shared inventory —
`.agents/brain/decisions/2026-04-30-annona-shared-household-data.md`.
